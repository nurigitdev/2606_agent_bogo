# 층간 배포 가이드 — 서로 다른 망/PC 를 한 중앙 서버에 연결

이 문서는 **여러 망·여러 PC**(예: 6·7·10층의 직원 노트북, 대표 노트북)에서 BOGO
사내 보고 시스템을 함께 쓰는 **중앙 서버(층간) 모드** 배선을 설명한다.

흐름:

```
[A망 직원 브라우저] ─┐
[B망 직원 브라우저] ─┼─▶ [중앙 서버 1대: NIC 3장 + Mattermost + 팀봇/CEO봇(헤르메스 두뇌)]
[C망 직원 브라우저] ─┘                        │
                                              └─▶ [대표 브라우저: CEO 대시보드]
```

핵심: 직원·대표·봇 두뇌가 **같은 한 대의 Mattermost 서버**에 붙어야 메시지가 한 곳에
모인다. 서로 다른 망/IP 가 그 서버를 찾아갈 **사설 네트워크 경로**가 필요하다 —
이 문서가 그 경로를 세 가지 방식으로 제공한다(권장: 멀티홈 다중 NIC 직결).

> **단일 PC 모드는 이 문서가 필요 없다.** 한 대의 PC 에서 직원·봇·대표가 모두
> 도는 데모/소규모 운영은 아무 환경변수도 건드리지 않으면 자동으로 `127.0.0.1`
> 루프백 전용(외부 노출 0)으로 동작한다. README 의 "단일 PC 모드"를 따른다.

> **세 가지 연결 방식 한눈에:**
> | 방식 | 언제 | 외부 노출 |
> |------|------|----------|
> | **1. 멀티홈(다중 NIC 직결)** — 권장 | 물리 분리된 사내망이 같은 건물에 있고 서버실에 랜선 포설 가능 | 0 (공인 NIC 부재 + 방화벽 이중 가드) |
> | 2. Tailscale 메시 VPN — 대안 | 망이 흩어져 있거나 재택 포함, 랜선 포설 불가 | 0 (사설 메시) |
> | 3. 같은 LAN 직결 — 대안 | 모든 PC 가 같은 공유기/스위치 | 0 (사내 LAN 한정) |

## 0. 용어와 역할

| 역할 | 무엇을 하나 | 어디서 도나 |
|------|------------|------------|
| **중앙 서버** | Mattermost + Postgres + 팀봇/CEO봇 두뇌 + CEO 대시보드 | 한 대의 고정 PC/서버(예: DGX, 상시 켜진 데스크탑) |
| **직원 PC(7층)** | 데스크탑 앱(또는 브라우저)으로 자기 팀 채널에 보고 업로드 | 직원 각자의 노트북 |
| **대표 PC(10층)** | 브라우저로 CEO 대시보드 접속, 현황 보기·지시 | 대표 노트북 |

핵심 변수(전부 `.env.example`에 주석과 함께 있음):

| 변수 | 의미 | 누가 설정 | 기본값 |
|------|------|----------|--------|
| `MM_HOST` | 봇·대시보드·프로비저너가 **붙는** Mattermost 호스트 | 모든 PC | `127.0.0.1` |
| `MM_PORT` | Mattermost 포트 | 모든 PC | `8065` |
| `MM_BIND_HOST` | Mattermost 컨테이너가 **받는** 바인딩 호스트 | 중앙 서버만 | `127.0.0.1` |
| `MM_SITE_URL` | 클라이언트 접속 표준 주소(WebSocket·로그인 리다이렉트 기준) | 중앙 서버만 | `http://127.0.0.1:8065` |
| `MM_ALLOW_CORS_FROM` | 추가 접속 오리진(멀티홈에서 B/C 망 IP — 공백 구분) | 중앙 서버(멀티홈)만 | 빈 값 |
| `BOGO_MULTIHOME` | 멀티홈 모드 스위치(`1`이면 `0.0.0.0` 바인딩 허용) | 중앙 서버(멀티홈)만 | 미설정(=off) |
| `BOGO_DASHBOARD_HOST` | CEO 대시보드 웹앱 바인딩 호스트 | 중앙 서버만 | `127.0.0.1` |
| `BOGO_DASHBOARD_PORT` | CEO 대시보드 포트 | 중앙 서버만 | `8642` |

## 1. 권장: 멀티홈(다중 NIC 직결) 중앙 서버 1대

같은 건물에 입주한 **물리적으로 분리된 사내망 3개**(예: 10·9·8층=A망, 7층=B망,
6층=C망)를 한 중앙 서버에 묶는 방식이다. 서버 한 대에 **랜카드(NIC) 3장**을 꽂아
각 망 스위치에 직결한다(서버실 상하 통로로 랜선 포설). 이 서버가 Mattermost +
Postgres + 팀봇/CEO봇(헤르메스 두뇌) + CEO 대시보드를 **전부** 돌린다. 각 망 직원은
자기 망에서 해당 NIC 의 사설 IP 로 **브라우저만으로** 접속한다(클라이언트 설치 0).

```
            ┌──────────────── 중앙 서버 1대 ────────────────┐
[A망 스위치]─┤ NIC-A (예: 10.0.0.10)                          │
[B망 스위치]─┤ NIC-B (예: 172.16.0.10)   Mattermost+봇+대시보드 │
[C망 스위치]─┤ NIC-C (예: 192.168.50.10)                       │
            └────────────────────────────────────────────────┘
              ↑ 인터넷 향 NIC 없음(공인 IP 0) → 외부 노출 원천 불가
```

### 1-1. 왜 멀티홈이 권장인가 (보안·운영 근거)

- **외부 노출이 원천 불가.** 인터넷 향 NIC 가 아예 없어(공인 IP 0) 어떤 포트를
  열어도 사내 3개 사설망 밖으로는 패킷이 나갈 경로가 없다. 포트포워딩·VPN·터널이
  불필요하고, 그래서 잘못 열 위험 자체가 없다.
- **클라이언트 설치 0.** 직원은 브라우저로 자기 망 NIC IP 에 접속만 하면 된다.

### 1-2. NIC 3장 물리 배선 + 사설 IP 할당

1. 중앙 서버에 NIC 3장을 장착하고, 각 NIC 를 A/B/C 망 스위치에 랜선으로 직결한다
   (서버실 상하 통로로 포설). 같은 대표가 3개 망을 소유하므로 연결 승인은 완료.
2. 각 NIC 에 해당 망 대역의 **고정 사설 IP** 를 부여한다. 세 망이 대역이 겹치지
   않도록 한다(예: A=`10.0.0.10/24`, B=`172.16.0.10/24`, C=`192.168.50.10/24`).
   ```bash
   # Linux 예시(인터페이스명은 환경마다 다름 — ip link 로 확인)
   ip -4 addr show           # 각 NIC 에 IP 가 붙었는지 확인
   ```

### 1-3. 중앙 서버 `.env` 설정 (멀티홈 활성화)

중앙 서버 `app/.env`(`.env.example` 복사 후 수정)에 다음을 넣는다:

```bash
# 멀티홈 모드 켜기 — 이 플래그가 있어야 0.0.0.0 바인딩이 허용된다.
BOGO_MULTIHOME=1

# Mattermost·대시보드를 3개 NIC 전부에서 받는다. 단일 listen 소켓이라 IP 별
# 다중 바인딩이 불가하므로 0.0.0.0 으로 모든 NIC 를 동시에 수신한다.
# 공인 NIC 가 없으므로 0.0.0.0 은 사내 3개 사설망에만 노출된다.
MM_BIND_HOST=0.0.0.0
BOGO_DASHBOARD_HOST=0.0.0.0

# SiteURL 멀티액세스(아래 1-4 참고): 주 망(A) IP 를 SiteURL 로, 나머지 2개 망
# (B/C) 오리진을 AllowCorsFrom 에 공백 구분으로 등록한다.
MM_SITE_URL=http://10.0.0.10:8065
MM_ALLOW_CORS_FROM=http://172.16.0.10:8065 http://192.168.50.10:8065

# 봇은 서버 로컬에서 자기 Mattermost 에 붙으므로 MM_HOST 는 생략(기본 127.0.0.1).
# → 봇 경로는 SiteURL/CORS 의 영향을 전혀 받지 않는다(항상 안정).
```

인프라 (재)기동:

```bash
cd app
docker compose down && docker compose up -d      # MM_BIND_HOST/SiteURL/CORS 반영
# 봇 두뇌·대시보드 재시작(상시 가동 중이면 운영 명령으로 재배포 — README 참고)
```

### 1-4. SiteURL 멀티액세스 — 3개 망 동시 접속을 깨지지 않게 (핵심 난점)

Mattermost 9.x 는 **SiteURL 을 1개만** 가진다. A/B/C 3개 망에서 서로 다른 NIC IP 로
접속하면, SiteURL 에 없는 IP 의 **WebSocket 오리진이 `Upgrader.CheckOrigin` 에서
차단**되어 실시간 기능(새 글 즉시 표시 등)이 깨진다.

**채택안(Mattermost 공식 해법):** `AllowCorsFrom` 에 추가 오리진을 **공백 구분**으로
등록해 웹소켓 CheckOrigin·CORS 차단을 푼다. 즉,

- `MM_SITE_URL` = 주 망(A) IP 오리진 1개 (`http://10.0.0.10:8065`)
- `MM_ALLOW_CORS_FROM` = 나머지 2개 망(B/C) IP 오리진을 공백 구분
  (`http://172.16.0.10:8065 http://192.168.50.10:8065`)

> 근거: Mattermost Knowledge Base "Real-Time Features Not Working … When Connecting
> From Multiple Origins" — 추가 오리진의 WebSocket 연결은 `AllowCorsFrom` 에
> 공백 구분으로 등록해야 허용된다. `*`(전체 허용)도 가능하나 권장되지 않으므로,
> 노출 표면을 좁히기 위해 **B/C 망 IP 만 명시**한다.

**채택안의 제약(명시):**
- 이메일 알림·OAuth 콜백 등 **절대 URL 을 생성하는 일부 기능은 SiteURL(주 망 A)
  기준 링크**를 만든다 → B/C 망 직원이 그 링크를 클릭하면 A망 IP 라 자기 망에서
  안 열릴 수 있다. 사내 보고 흐름(채널 글·파일·실시간 표시·로그인)은 영향 없다.
- SiteURL 을 **빈 값**으로 두면 오리진 체크가 느슨해지지만, 데스크톱 앱의 서버 URL
  검증이 빈 SiteURL 에서 입력값을 지워버리는 알려진 이슈(mattermost/mattermost
  #25153)가 있어 **권장하지 않는다.** 그래서 SiteURL 명시 + AllowCorsFrom 다중
  오리진을 채택했다.

**봇 경로는 SiteURL 영향 없음(확인됨):** 봇은 `mm_client` 가 서버 로컬에서
`127.0.0.1:8065`(`MM_HOST` 기본값)로 자기 Mattermost 에 붙는다. WebSocket 오리진도
로컬이라 CheckOrigin 을 항상 통과한다 → 봇 두뇌(헤르메스)는 멀티홈 SiteURL 설정과
무관하게 동작한다.

### 1-5. 직원·대표 접속 (클라이언트 설치 0)

- **각 망 직원:** 자기 망에서 브라우저로 **해당 NIC IP** 의 Mattermost 에 접속한다.
  - A망(10·9·8층): `http://10.0.0.10:8065`
  - B망(7층):       `http://172.16.0.10:8065`
  - C망(6층):       `http://192.168.50.10:8065`
  프로비저닝으로 발급된 직원 계정(아래 4절)으로 로그인 후 자기 팀 채널에 보고한다.
- **대표:** 브라우저로 대시보드 NIC IP 에 접속한다(예: `http://10.0.0.10:8642`).
  자기 망의 NIC IP:8642 를 쓰면 된다. `ceo_auth` 로그인 게이트 뒤이므로 로그인
  없이는 아무것도 보이지 않는다.

### 1-6. 방화벽 인터넷 차단 (이중 가드)

공인 NIC 가 없는 것이 1차 가드지만, 안전을 위해 방화벽으로 인터넷 향(0.0.0.0/0)
아웃바운드/인바운드를 차단해 **이중 가드**한다. 서버는 사내 3개 망하고만 통신한다.

```bash
# Linux 예시(ufw) — 사내 3개 사설 대역만 허용, 그 외 차단
sudo ufw default deny incoming
sudo ufw allow from 10.0.0.0/24       to any port 8065,8642 proto tcp
sudo ufw allow from 172.16.0.0/24     to any port 8065,8642 proto tcp
sudo ufw allow from 192.168.50.0/24   to any port 8065,8642 proto tcp
sudo ufw enable
```

> 봇 두뇌가 **클라우드 LLM(OpenRouter)** 을 쓰면 아웃바운드 인터넷이 필요하다.
> 인터넷 향을 완전 차단하려면 `.env` 에 `LLM_BACKEND=local`(로컬 LLM)로 두어
> 외부 호출 0 으로 운영한다(mm_client 의 LLM 백엔드 스위치).

## 2. 대안: Tailscale 메시 VPN (방화벽·포트포워딩 없이 사내 전용 연결)

각 PC 가 다른 IP·다른 네트워크(사무실 Wi-Fi, 재택)에 있어도, Tailscale 이
PC 들을 하나의 사설 메시 네트워크(`100.x.x.x` 대역)로 묶는다. 공유기 포트포워딩,
공인 IP, 방화벽 설정이 **전혀 필요 없고**, 외부 인터넷에는 한 포트도 열리지 않는다.

### 1-1. 모든 PC 에 Tailscale 설치

각 PC(중앙 서버 + 직원 + 대표)에서 동일하게 1회 수행한다.

```bash
# macOS
brew install --cask tailscale     # 또는 App Store / tailscale.com 다운로드
# Linux (Ubuntu/Debian/DGX OS)
curl -fsSL https://tailscale.com/install.sh | sh
# Windows
#   tailscale.com/download 에서 설치 파일 다운로드 후 실행
```

설치 후 같은 조직 계정으로 로그인한다(`tailscale up`). 회사 단위로 하나의
tailnet 을 쓰면 모든 PC 가 자동으로 같은 사설망에 들어온다.

```bash
sudo tailscale up        # 브라우저 인증 → 회사 계정으로 로그인
tailscale ip -4          # 이 PC 의 Tailscale IPv4 주소(100.x.x.x) 확인
```

### 1-2. 중앙 서버 PC 설정

중앙 서버의 Tailscale IP 를 확인한다(예: `100.101.102.103`). 중앙 서버 PC 의
`app/.env` 에 다음을 넣는다(`.env.example` 복사 후 주석 해제·수정):

```bash
# 중앙 서버 자신이 붙는 주소(자기 자신이므로 루프백도 되지만 일관성 위해 자기 IP)
MM_HOST=100.101.102.103
MM_PORT=8065

# Mattermost 컨테이너가 이 IP 로 들어오는 접속을 받게 한다
MM_BIND_HOST=100.101.102.103
MM_SITE_URL=http://100.101.102.103:8065

# CEO 대시보드도 이 IP 로 받게 한다(대표 노트북 브라우저가 붙음)
BOGO_DASHBOARD_HOST=100.101.102.103
BOGO_DASHBOARD_PORT=8642
```

그다음 인프라를 (재)기동한다:

```bash
cd app
docker compose down && docker compose up -d      # MM_BIND_HOST/MM_SITE_URL 반영
# 봇 두뇌·대시보드 재시작(상시 가동 중이면 운영 명령으로 재배포 — README 참고)
```

### 1-3. 직원 PC(7층) 설정 — 데스크탑 앱

직원 PC 에는 무거운 인프라가 필요 없다. **중앙 서버를 가리키게만** 하면 된다.

- **Mattermost 데스크탑 앱 사용(가장 쉬움):**
  앱 설치 후 서버 주소에 `http://100.101.102.103:8065`(= 중앙 서버 `MM_SITE_URL`)를
  입력하고, 프로비저닝으로 발급된 직원 계정(아래 3절)으로 로그인한다. 직원은 자기
  팀 채널에 글·파일을 올리면 그게 곧 "보고 업로드"다.
- **브라우저 사용:** 브라우저에서 `http://100.101.102.103:8065` 접속.
- **직원 PC 에서 봇 두뇌까지 돌릴 경우(드묾):** 직원 PC `app/.env` 에
  `MM_HOST=100.101.102.103` 만 지정(`MM_BIND_HOST`·`MM_SITE_URL` 은 중앙 서버만
  필요하므로 생략).

### 1-4. 대표 PC(10층) 설정 — CEO 대시보드 접속

대표 PC 는 브라우저만 있으면 된다.

```
브라우저에서  http://100.101.102.103:8642  접속
→ ceo_auth 로그인 화면 → 대표 계정으로 로그인 → 부서 현황·지시 화면
```

대시보드는 인증 게이트(ceo_auth 세션 쿠키) 뒤에 있으므로, 메시 안의 사설 IP
바인딩이라도 로그인 없이는 아무것도 보이지 않는다.

## 3. 대안: 같은 사내 LAN 직결 (모든 PC 가 같은 공유기/스위치)

모든 PC 가 **같은 사무실 LAN**(같은 공유기/스위치)에 있다면 Tailscale 없이
사내 사설 IP(`192.168.x.x` 또는 `10.x.x.x`)로 직접 연결할 수 있다.

1. 중앙 서버 PC 의 사내 IP 확인:
   ```bash
   # macOS / Linux
   ipconfig getifaddr en0     # mac 유선/Wi-Fi (인터페이스명은 환경마다 다름)
   ip -4 addr show            # Linux
   # Windows
   ipconfig                   # IPv4 주소 항목
   ```
   예: `192.168.0.50`.
2. 중앙 서버 `app/.env` 에 그 IP 를 넣는다(1-2절과 동일하되 `100.x` 대신 `192.168.x`):
   ```bash
   MM_HOST=192.168.0.50
   MM_BIND_HOST=192.168.0.50
   MM_SITE_URL=http://192.168.0.50:8065
   BOGO_DASHBOARD_HOST=192.168.0.50
   ```
3. 직원 PC: 데스크탑 앱/브라우저 서버 주소에 `http://192.168.0.50:8065`.
4. 대표 PC: 브라우저로 `http://192.168.0.50:8642`.

> LAN 직결은 **같은 네트워크 안에서만** 닿는다. 재택·다른 층 분리망·외부에서
> 접속이 필요하면 1절 Tailscale 을 쓴다(권장). LAN 직결을 쓰더라도 공유기에서
> 외부(WAN) 포트포워딩은 절대 열지 않는다 — 사내망 안에서만 닿아야 한다.

## 4. 직원 계정 프로비저닝 (층간 모드에서 직원이 로그인하려면)

직원 PC 로그인에 쓸 Mattermost 계정을 중앙 서버에서 **한 번** 발급한다.

1. 중앙 서버 `app/` 에서 명단 파일을 만든다:
   ```bash
   cp employees.json.example employees.json
   ```
2. `employees.json` 을 실제 직원으로 채운다. 각 직원의 `team_channels` 는
   `channels.json` 에 실재하는 한글 채널명이어야 한다(예: `"개발팀"`,
   `"개발-보고라인"`). 정의되지 않은 채널은 경고 후 자동 skip 된다(라우팅 보호).
   `password` 는 직원에게 전달할 **초기 비밀번호**(첫 로그인 후 변경 권장).
3. 프로비저닝을 실행한다(인프라 기동 후):
   ```bash
   .venv/bin/python provision_mm.py
   ```
   직원 계정이 멱등 생성되고(이미 있으면 skip), 각 직원이 소속 팀·채널 멤버로
   배치된다. 비밀번호는 표준출력에 노출되지 않는다.

> `employees.json` 은 초기 비밀번호 평문을 담으므로 **시크릿**이다.
> `.gitignore` 가 커밋을 차단하며, git 에는 `employees.json.example`(플레이스홀더)만
> 추적된다. 단일 PC 데모는 `employees.json` 을 두지 않으면 이 단계가 자동 skip 된다.

## 5. 보안 경계 (불변 — 절대 위반 금지)

- **외부(공인 인터넷) 노출 0.** 모든 연결은 사내 LAN, Tailscale 사설 메시, 또는
  멀티홈의 사내 사설망 3개 안에서만 일어난다. 공유기 WAN 포트포워딩·공인 IP 직접
  노출·ngrok 같은 공개 터널을 **금지**한다.
- **와일드카드 바인딩은 멀티홈 모드에서만 허용.** `0.0.0.0` / `::` 같은 "모든
  인터페이스" 바인딩은 기본·LAN·Tailscale 모드에서 공인 NIC 까지 열릴 위험이 있어
  **거부**된다. 단, **멀티홈 모드(`BOGO_MULTIHOME=1`)** 는 서버에 공인 NIC 가 없고
  (공인 IP 0) 사내 사설망 3개에만 NIC 직결된 환경이므로, 3개 NIC 를 단일 listen
  소켓으로 동시에 받기 위해 `0.0.0.0` 을 **허용**한다(인터넷 향 차단은 공인 NIC
  부재 + 방화벽 이중 가드). `*` 는 어떤 모드에서도 유효 바인딩이 아니라 항상 거부.
  - `MM_BIND_HOST`: LAN/Tailscale 은 **특정 사설 IP**, 멀티홈은 `0.0.0.0`.
  - `BOGO_DASHBOARD_HOST` 에 와일드카드를 넣으면, `BOGO_MULTIHOME=1` 이 아닌 한
    코드가 이를 **거부하고 자동으로 `127.0.0.1` 로 강등**한다(경고 출력).
    멀티홈 모드에서만 `0.0.0.0` 바인딩이 통과한다(인증 게이트는 그대로 유지).
- **대시보드는 인증 게이트(ceo_auth) 뒤에 둔다.** 사설 IP 로 바인딩하더라도
  로그인 세션 없이는 데이터·지시 API 가 열리지 않는다. 봇 토큰·세션 쿠키는
  HttpOnly·SameSite=Strict 로 보호된다.
- **시크릿은 커밋하지 않는다.** `.env`, `employees.json`, `*_config.json`,
  `channels.json` 은 `.gitignore` 로 차단되고, git 에는 `*.example` 만 추적된다.
- **기본값은 항상 안전하다.** 환경변수를 하나도 설정하지 않으면 전부 `127.0.0.1`
  루프백 전용으로 떨어진다 — 잘못 설정해도 외부로 새지 않는 게 기본 동작이다.

## 6. 연결 점검 체크리스트

### 6-1. 멀티홈(다중 NIC) 모드 점검

| 점검 | 명령/방법 | 기대 |
|------|----------|------|
| NIC 3장 IP | 중앙 서버에서 `ip -4 addr show` | A/B/C 망 사설 IP 3개 보임 |
| A망 MM 도달 | A망 직원 PC 에서 `curl http://10.0.0.10:8065/api/v4/system/ping` | `{"status":"OK"}` |
| B망 MM 도달 | B망 직원 PC 에서 `curl http://172.16.0.10:8065/api/v4/system/ping` | `{"status":"OK"}` |
| C망 MM 도달 | C망 직원 PC 에서 `curl http://192.168.50.10:8065/api/v4/system/ping` | `{"status":"OK"}` |
| 실시간 동작(웹소켓) | B/C 망 브라우저에서 로그인 후 글 작성 → 즉시 표시 | 새 글이 새로고침 없이 뜸(= AllowCorsFrom 정상) |
| 대시보드 | 대표 브라우저 `http://<자기망 NIC IP>:8642` | 로그인 후 현황 카드 |
| 봇 경로(로컬) | 중앙 서버에서 `curl http://127.0.0.1:8065/api/v4/system/ping` | `{"status":"OK"}` (봇은 이 경로) |
| 외부 차단 확인 | 사내 3개 망 **밖**(인터넷)에서 서버로 접속 시도 | 도달 경로 없음(공인 NIC 부재) |

연결이 안 되면: ① 중앙 서버 `.env` 에 `BOGO_MULTIHOME=1` + `MM_BIND_HOST=0.0.0.0`
이 있는지, ② `docker compose down && up -d` 재기동으로 바인딩·SiteURL·CORS 가
반영됐는지, ③ B/C 망에서 **실시간만** 안 되면 `MM_ALLOW_CORS_FROM` 에 그 망 IP
오리진(`http://IP:8065`)이 공백 구분으로 들어갔는지, ④ 각 NIC 에 고정 사설 IP 가
붙었는지(`ip -4 addr show`) 순서로 확인한다.

### 6-2. Tailscale·LAN(단일 IP) 모드 점검

| 점검 | 명령/방법 | 기대 |
|------|----------|------|
| 메시 연결 | 직원 PC 에서 `tailscale ping <중앙서버 IP>` | 응답 OK |
| MM 도달 | 직원 PC 에서 `curl http://<중앙서버 IP>:8065/api/v4/system/ping` | `{"status":"OK"}` |
| 직원 로그인 | 데스크탑 앱/브라우저에서 직원 계정 로그인 | 자기 팀 채널 보임 |
| 보고 흐름 | 직원이 팀 채널에 글 작성 | 팀봇 응답 → CEO봇 게이트 |
| 대시보드 | 대표 PC 브라우저 `http://<중앙서버 IP>:8642` | 로그인 후 현황 카드 |
| 외부 차단 확인 | 사내망 **밖**에서 `curl http://<중앙서버 공인IP>:8065` | 연결 실패(정상) |

연결이 안 되면: ① 중앙 서버 `.env` 의 `MM_BIND_HOST`/`MM_SITE_URL` 이 같은
IP:포트인지, ② `docker compose up -d` 재기동으로 바인딩이 반영됐는지, ③ 직원 PC
`MM_HOST` 가 중앙 서버 IP 와 일치하는지, ④ Tailscale 이 양쪽에서 `up` 상태인지
순서로 확인한다.
